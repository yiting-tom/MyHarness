# 設計：逐輪軌跡視圖

## 這一層要回答的問題

派工層已經有答案的：**這份報告是根據什麼寫出來的。**
這一層要補的：**那一步到底是怎麼做出來的。**

兩個問題分在兩個工具裡就等於沒有答案 —— 過去四次診斷都是在 `inspect` 看到
`status=budget_exceeded`，然後開一支臨時腳本去翻 transcript。視圖的成敗就看
這兩者能不能在同一個畫面裡互相到達。

## 三個既有事實決定了版面

1. **流向是有向的，而且很淺。** blob → dispatch → finding → report，四層。
   不需要力導向圖 —— 那會把一個本來就是樹的東西畫成一團毛線。畫成**縮排的樹**，
   邊的字形沿用 `inspect` 的 `←授權` / `→產出`。
2. **軌跡是一維的。** turn 是嚴格有序的，所以是**時間軸**，不是圖。
   編號在這裡是合法的結構資訊（真的有先後），不是裝飾。
3. **帳是分欄的數字。** token 進、出、估計、回報 —— 表格，等寬數字。

→ **三欄：流向（樹）· 軌跡（時間軸）· 帳（表）。** 一次選取同時驅動右邊兩欄。

## 視覺語言從終端機來，不從 dashboard 來

既有的 `render.py` 用的是 ANSI 16 色與 `▣ ▪ ★ ◇ ◆` 這組字形，而使用者每天看的
就是那個輸出。視圖如果換一套 dashboard 的視覺語言，讀者要在兩套符號之間翻譯。

所以調色盤是**精煉過的 ANSI**，不是任何 UI kit 的預設：

| token | 深色 | 淺色 | 用途 |
|---|---|---|---|
| `--ground` | `#0C1117` | `#F3F6F8` | 底 —— 冷偏藍的近黑，不是純灰 |
| `--cyan` | `#4EC9C0` | `#12776F` | 產出、執行中、選取（強調色） |
| `--green` | `#6BBF7B` | `#2F7B45` | ok |
| `--yellow` | `#D9B04A` | `#8A6410` | warning、授權了但沒讀 |
| `--red` | `#E0605A` | `#B3352E` | critical、工具錯誤 |
| `--magenta` | `#B98AD6` | `#6E479A` | 推理標記 —— 刻意跟其他四色都不像 |

`inspect` 裡 `→產出` 是 cyan、`running` 是 cyan、`ok` 是 green、warning 是 yellow、
critical 是 red —— 一個都沒改。

**字體**：JetBrains Mono 撐結構（派工 id、token 欄、SQL、工具名），
IBM Plex Sans 撐敘述，CJK 走系統堆疊。等寬體在這裡不是風格選擇：
transcript 裡有 SQL 和對齊的表格輸出，比例字體會把它們拆掉。

## 三件必須被看見的「沒有」

這是整個設計裡最重要的部分，也是最容易做錯的部分。

| 沒有的東西 | 為什麼沒有 | 視圖怎麼處理 |
|---|---|---|
| **推理文字** | `_block_to_dict` 只留 `chars` —— 一次執行會串流大量推理文字而其中沒有分析。而自架後端連字元數都是 0（回傳的是 53 bytes 的空殼） | 顯示一個推理標記，寫明「內容未留存」；`chars: 0` 再另外寫明「後端回傳空的推理區塊」。**兩者不同，不能合併** |
| **工具結果全文** | `_excerpt` 取頭 2/3 尾 1/3 | 保留資料裡原本就有的 `…[略過 N 字元]…`，並加節錄標記 |
| **精確的 token 數** | 執行被中途停止時後端不會送出帶 usage 的訊息 | 沿用 `inspect` 的 `~` 前綴 |

**失敗模式很具體**：把工具呼叫排成一列、標題寫「推理過程」。
那讓一份不存在的紀錄看起來存在，而且看起來很有說服力。
這條規則跟「授權邊不冒充讀取邊」是同一條 —— 那條規則寫進 spec 是有代價才學會的。

## 預算條

沿軌跡左緣的一條直向量尺，隨 turn 累積填滿，並標出 harness 實際發出警告的位置
與閘門的門檻。

這是唯一一個「新畫出來的東西」，理由是 golden #23 與 #24 的差別**只存在於這個維度**：

- #23 d1：13 次查詢 → `artifact: null`（預算耗盡時還沒開始寫）
- #24 d1：57% 時被警告「只夠再 5 次請求」→ **下一輪就寫完了** → 帶著 finding 撞線

兩者的 `status`、`tokens`、`turns` 都在 `inspect` 裡，而「在哪一輪轉向」不在任何
既有輸出裡。

## 不做什麼

- **不用圖表函式庫。** 這裡唯一的「圖」是一條長條與一棵縮排的樹，
  兩者都是幾個 div。引入 D3 換到的是視覺不是資訊 —— 跟 `render.py`
  不用 rich / textual 是同一個判斷。
- **不做即時模式。** `monitor` 已經有即時模式而且是終端機的。
  瀏覽器裡的即時模式需要一個 server，那就違反了「零新增相依」。
- **不做力導向圖。** 見上。
- **不做 hover 才出現的資訊。** 這是要被截圖貼進 issue 的東西。
- **手機版不是目標。** 這是在筆電上看 transcript 的工具。窄螢幕要能讀（三欄疊成一欄），
  但觸控目標尺寸、安全區域、底部導覽那一套跟這個產品無關，不假裝適用。

## 一個有意識的取捨：全文內嵌

transcript 是 **blob** —— 契約上絕不能被讀進任何 context。
內嵌進一份給人看的 HTML 不違反那條（人不是 context），但它意味著產出的檔案
**含有原始資料的片段**。

所以：預設寫到 stdout，不寫進 job 目錄，也不自動分享。
golden24 三份 transcript 共 81KB，內嵌沒問題；50 次派工的 job 要先量過
（tasks 1.4）再決定要不要改成按需載入。
